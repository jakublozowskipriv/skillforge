# Testy, kontrakty, materializacje i incremental

Masz warstwy (lekcja 1) i gwiazdę z jasnym grainem (lekcja 2). Ta lekcja jest o tym, żeby to
**nie psuło się po cichu** i żeby **budowało się tanio**. Z Airflow znasz kontrole jakości
i reprocessing — dbt przenosi oba tematy do repo, obok SQL-a modeli.

## 1. Test w dbt to zapytanie, które zwraca błędy

To najważniejsza intuicja: **każdy test dbt to SELECT zwracający wiersze łamiące regułę**.
Zero wierszy = zielono. Test `unique` na `shipment_id` kompiluje się mniej więcej do:

```sql
select shipment_id, count(*) as n
from marts.fct_shipments
group by shipment_id
having count(*) > 1
```

Rodzaje testów:

| Rodzaj | Gdzie | Przykład z projektu |
|---|---|---|
| **generic** (wbudowane) | YAML | `unique`, `not_null`, `accepted_values`, `relationships` |
| **generic** (własne) | `tests/generic/*.sql` | `unique_combination_of_columns` na `(shipment_id, event_type, event_at)` |
| **singular** | `tests/*.sql` | `assert_delivered_after_pickup` |
| **unit test** (dbt ≥ 1.8) | YAML `unit_tests:` | `test_carrier_code_is_normalized` — sztuczne wiersze wejściowe → oczekiwane wyjście |

Data testy sprawdzają **dane**, unit testy sprawdzają **logikę SQL** na spreparowanych
przypadkach brzegowych — także takich, których jeszcze nie ma w danych (np. kod `' swift'`).

**Gdzie testować?** Źródła — żeby wykryć problem zanim się rozleje (`unique` na `event_id`
w `raw`). Klucze grainu każdego martu (`unique` + `not_null`). Relacje fakt → wymiar
(`relationships`). Reguły biznesowe, które łatwo złamać (doręczenie przed odbiorem).

Testy mają `severity` (`warn` / `error`) i `where:` — np. `carrier_sla_key` nie może być NULL,
ale tylko dla przesyłek już odebranych (`where: "picked_up_at is not null"`).

## 2. Kontrakty: obietnica co do kształtu

Test sprawdza dane *po* zbudowaniu modelu. **Kontrakt** (`contract: enforced: true`) sprawdza
*przed*: nazwy kolumn, typy i constraints muszą zgadzać się z YAML, inaczej `dbt build`
w ogóle nie utworzy tabeli. `fct_shipments` ma kontrakt — jeśli ktoś zmieni `is_on_time`
z `boolean` na `integer`, build się zatrzyma, zanim dashboard dostanie zera i jedynki.

Kontrakt to interfejs martu dla konsumentów: BI, notebooków i agentów text-to-SQL. Zmiana
kontraktu = zmiana API, więc robi się ją świadomie (w dbt: wersje modeli).

## 3. Kontrakt metryki: licznik i mianownik

Ta sama dyscyplina dotyczy metryk. „Reklamacje na 1000 przesyłek” wymaga ustalenia:
**co jest w liczniku** (wszystkie reklamacje? tylko zaakceptowane?), **co w mianowniku**
(nadane? doręczone?), **w jakim oknie czasu** i **na jakim grainie** liczymy. Warstwa
semantyczna (LookML, dbt Semantic Layer) to właśnie miejsce, gdzie tę definicję zapisujesz
raz — a wszyscy, łącznie z agentami, liczą z niej, zamiast pisać własny SQL.

## 4. Materializacje

| Materializacja | Co tworzy | Kiedy |
|---|---|---|
| `view` | widok | staging, intermediate — tanie, zawsze świeże |
| `table` | tabela przebudowywana w całości | marty — szybkie zapytania, stabilny interfejs |
| `incremental` | tabela dopisywana przyrostowo | duże, rosnące fakty (eventy) |
| `ephemeral` | CTE wklejane do zależnych modeli | małe klocki, których nikt nie odpytuje |

## 5. Incremental i spóźnione dane

`fct_shipment_events` przy każdym runie przetwarza tylko nowe dane:

```sql
{% if is_incremental() %}
where loaded_at > (
    select max(loaded_at) - interval {{ var('event_lookback_days') }} day from {{ this }}
)
{% endif %}
```

Trzy decyzje w tych pięciu linijkach:

1. **Filtrujemy po `loaded_at`, nie po `event_at`.** Przewoźnik może przysłać event z poniedziałku
   w czwartek. Filtr po `event_at >= ostatni_run` by go zgubił na zawsze — bo jego `event_at`
   jest „stary”, choć do nas dotarł dopiero teraz.
2. **Lookback** (3 dni) — czytamy też trochę „wstecz”, żeby złapać dane dociągnięte z opóźnieniem
   po stronie EL. To ten sam pomysł co reprocessing ostatnich N partycji w Airflow.
3. **`unique_key`** — przeczytane drugi raz wiersze są nadpisywane, nie dublowane. Bez klucza
   lookback produkowałby duplikaty.

`--full-refresh` przebudowuje tabelę od zera — np. po zmianie logiki albo, jak u nas,
gdy `skillforge data build` generuje dane od nowa.

## Jak zastosować w pracy

- **Przepisz jedną kontrolę jakości z Airflow na „zapytanie zwracające błędne wiersze”.**
  Nawet bez dbt: widok `dq_<reguła>` + alert, gdy `count(*) > 0`. To ten sam kontrakt co test dbt,
  a łatwo go później przenieść.
- **Zrób przegląd filtrów przyrostowych** w swoich DAG-ach: czy filtrują po czasie zdarzenia,
  czy po czasie załadowania? Policz (jak w ae-ex-09), ile spóźnionych rekordów gubi wariant
  naiwny — to konkretna liczba do brag doca.
- **Spisz definicję jednej metryki dostaw** w formacie: licznik / mianownik / okno / grain /
  wykluczenia. Porównaj z tym, jak liczą ją 2–3 dashboardy. Rozjazdy to gotowa rekomendacja.
